## 完整使用者需求原文

# 執行規則：可中斷、可恢復

本次任務可能因 Codex 額度耗盡、上下文壓縮或工作階段中斷而無法一次完成。

請將整個任務設計為可以跨對話恢復的工作流程，不可只依賴聊天紀錄保存進度。

## 1. 建立持久化任務文件

開始任何程式修改前，請建立或更新：

- `docs/acceptance-plan.md`：完整任務需求、執行順序及各項驗收標準。
- `docs/acceptance-progress.md`：目前進度、修改紀錄、測試證據、待處理問題及恢復指引。

請將本次 Prompt 的完整需求保存到計畫文件，不可只記錄摘要，避免新對話遺失限制條件。

若文件已存在，先閱讀並核對，不得直接覆蓋既有紀錄。

## 2. 分階段執行

按照以下順序進行：

- P0：現況調查、建立任務文件及確認基準。
- P1：炭灰主題預設值、外觀設定分頁及設定持久化。
- P2：主題切換完整性及跨頁面回歸測試。
- P3：其他功能 Bug 檢查及本次改動造成的問題修復。
- P4：客製化 CSS／主題編輯器可行性評估（禁止實作）。
- P5：整合測試、最終驗收報告。

每階段都應有獨立的完成條件與測試結果。

## 3. 進度保存規則

每完成一個可獨立驗證的小步驟，立即更新進度文件。

至少記錄：

- 各階段狀態：Pending／In Progress／Done／Blocked。
- 已完成的修改及涉及的檔案。
- 已執行的測試、實際結果及失敗原因。
- 尚未完成的工作。
- 當前已知 Bug。
- 尚未確認的假設與風險。
- 下一步應執行的具體操作。

只有實際完成且通過驗證的步驟才能標記 Done。

## 4. 中斷恢復規則

每次開始或恢復工作時：

1. 閱讀 `docs/acceptance-plan.md` 與 `docs/acceptance-progress.md`。
2. 檢查 Git 工作區狀態及實際檔案差異。
3. 核對紀錄與目前程式碼是否一致。
4. 先確認上次中斷時是否留下未完成或無法編譯的修改。
5. 從第一個未完成或未驗證的步驟繼續。

不得因為進度文件標示完成，就跳過必要的核對。

不要重複執行已完成的修改，也不得直接覆蓋使用者或其他工作階段的變更。

若進度文件與程式碼存在衝突，以實際檔案狀態為調查起點，記錄差異後再決定如何繼續。

## 5. 額度與工作量控制

- 優先完成 P1 的必要功能。
- 避免不必要的全面重構。
- 優先使用現有測試工具。
- 測試範圍與深度應符合風險。
- 若無法一次完成所有階段，保留清楚的恢復資訊。
- 不要因為剩餘工作很多而跳過測試或草率宣告完成。
- 不要自行 Commit、Push 或部署。

如無法可靠判斷剩餘額度，不得假裝知道。

## 6. 每次回報

每次階段完成時，簡短回報：

- 已完成哪些事項。
- 通過哪些測試。
- 尚有哪些未完成事項。
- 下一步要做什麼。

以專案中的進度文件作為跨對話交接依據，而非聊天摘要。

# Freelance Tracker｜主題系統收尾與全面驗收

請先閱讀目前專案結構、既有主題系統及相關設定流程，確認實際實作狀態後，再執行以下任務。

本次目標：

1. 完成主題切換功能的收尾與整合。
2. 全面檢查主題系統及其他功能是否存在 Bug 或回歸問題。
3. 評估未來支援使用者客製化外觀的可行性。

請優先沿用現有架構，避免不必要的大規模重構。

## 第一階段：主題系統調整（需要實作）

### 1. 修改預設主題

- 將目前的「炭灰色版本」設為新使用者的預設主題。
- 已經手動選擇其他主題的使用者，應保留原本的選擇，不可被預設值覆蓋。
- 確保重新整理網頁、重新開啟瀏覽器後，主題選擇仍然有效。
- 檢查首次載入時是否會短暫閃現錯誤主題（FOUC）。

### 2. 整合主題切換入口

- 將目前散落在其他頁面的外觀切換功能，統一移至「設定」頁面。
- 在設定頁面新增一個「外觀」子分頁，沿用現有設定子分頁的設計與互動模式。
- 在「外觀」子分頁中提供所有現有主題的切換功能。
- 使用者選擇主題後，應立即預覽套用結果，並自動儲存。
- 清楚標示目前使用的主題。
- 移除原先重複的切換入口，避免出現多個互相衝突的控制位置。
- 不要刪除任何既有主題。

### 3. 主題儲存

- 優先沿用專案目前使用的設定儲存機制。
- 檢查是否存在多個主題狀態來源，避免頁面與設定資料不同步。
- 若有舊版主題設定資料，應考慮向下相容。
- 不應因切換主題而影響任務、專案或其他使用者資料。

## 第二階段：全面 Bug 與回歸測試

請實際檢查程式碼及可執行的功能，不要只根據表面結構推測沒有問題。

### A. 主題系統

- 所有現有主題是否能正常切換。
- 各頁面、彈窗、下拉選單、表單是否完整套用主題。
- 是否有寫死的顏色、遺漏的主題變數或樣式覆蓋衝突。
- Hover、Focus、Disabled、Selected、Error 等互動狀態是否正常。
- 文字、背景、邊框與提示訊息的對比是否合理。
- 主題切換是否引起不必要的重新渲染、版面跳動或閃爍。
- 重新整理、切換分頁、重新開啟網站後是否維持設定。

### B. 其他功能回歸

重點檢查主題改動是否間接影響：

- 專案群組與任務一覽。
- 任務新增、編輯、刪除及狀態切換。
- 搜尋、篩選與排序。
- 設定頁面及其所有子分頁。
- 彈窗、提示訊息、選單及其他互動元件。
- 資料儲存、讀取、匯入與匯出（若專案有實作）。
- 響應式版面與不同螢幕尺寸。

如發現其他明顯且可確認的 Bug，也請一併記錄。

### C. 檢查方式

- 執行專案現有的 Lint、Type Check、Build 及測試（以實際可用的指令為準）。
- 若有瀏覽器測試環境，請實際操作主要功能及主題切換流程。
- 若能取得畫面截圖，請以實際渲染結果進行視覺審查。
- 不可把「程式碼看起來正常」當成「功能已驗證通過」。
- 區分已實際測試、僅靜態檢查與尚未測試的項目。

發現與本次主題調整直接相關的 Bug，請修復並重新驗證。

若發現其他獨立功能的問題，請先列入報告，不要擅自大幅修改。

## 第三階段：客製化外觀可行性評估（只分析，不實作）

我希望未來能讓使用者自行客製化網站外觀，類似 Plurk 提供自訂 CSS 的功能。

請分析：

1. 現有主題系統是否已經具備擴充基礎？
2. 若開放使用者自訂 CSS，需要修改哪些架構？
3. 是否更適合先提供簡易主題編輯器，例如自訂背景色、卡片色、文字色、強調色等？
4. 自訂 CSS 與視覺化編輯器能否共存？
5. 如何讓自訂樣式只影響外觀，不破壞功能與操作？
6. 如何處理使用者輸入的 CSS 帶來的安全性、相容性與維護風險？
7. 如何提供一鍵還原預設外觀、匯入與匯出自訂主題？
8. 在 GitHub Pages 靜態部署環境下，哪些方案不需要後端服務？

請提出至少三種實作方案，並比較：

- 開發難度
- 維護成本
- 使用者自由度
- 安全性與穩定性
- 與現有架構的相容性

最後推薦最適合目前 Freelance Tracker 規模的方案，並說明是否值得現在開發，或留待未來版本。

**此階段禁止直接實作。**

## 第四階段：驗收報告

完成後請提供以下內容：

### 1. 實作摘要

- 實際修改了哪些功能。
- 修改了哪些檔案。
- 是否新增或調整設定資料結構。

### 2. 測試結果

使用表格列出：\
測試項目／測試方式／結果／問題與處理。

結果需區分：

- 通過
- 發現問題並已修復
- 未通過
- 未測試（說明原因）

### 3. Bug 清單

按照嚴重度分類：

- Critical：造成資料損毀或核心功能不可用
- High：主要功能明顯異常
- Medium：局部功能或互動問題
- Low：輕微視覺或使用體驗問題

### 4. 客製化外觀評估

提供方案比較、推薦架構及預估實作工作量。

### 5. 最終驗收結論

請明確說明：

- 本次需求是否完成。
- 是否仍有尚未解決的 Bug。
- 是否存在資料相容性或更新風險。
- 是否適合正式部署至 GitHub Pages。
- 還有哪些需要人工操作驗證的項目。

## 執行原則

1. 先理解現有實作，不要重新發明已存在的功能。
2. 優先最小範圍修改，避免破壞已穩定運作的部分。
3. 保護現有使用者資料與設定。
4. 不要為了通過測試而刪除測試、停用檢查或掩蓋錯誤。
5. 不得宣稱未實際執行的測試已通過。
6. 客製化外觀僅進行可行性分析，不得自行開發。
7. 不要自行部署、推送遠端或建立發行版本。
8. 如果遇到會影響現有資料或需要重大架構調整的決策，先停止該部分並說明風險。

請依照階段執行，完成後提供完整驗收報告。
